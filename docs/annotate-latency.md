# 단어 로딩 속도 개선 (annotate 지연 시간)

브랜치: `perf/annotate-latency`

단어가 뜨기까지 걸리는 시간을 줄이려고 세 가지를 바꿨다.

1. 모델 출력 줄이기
2. 서버 인증 왕복 없애기
3. 화면 근처 문단만 요청하기

이 문서는 각 변경의 **적용 전 / 적용 후**, **트레이드오프**, **되돌리거나 조절하는 방법**을 적어 둔다.

> 수치는 문단 길이(약 60단어), 단어 수 같은 **가정으로 계산한 추정치**다. 실제 값은 아래 "측정 방법"의 로그로 확인한다.

---

## 처리 흐름

```
적용 전
content.js ─(스크롤·DOM 변화마다 페이지 전체 스캔)─► background ─► Edge Function
  ─► auth.getUser() (Auth 서버 왕복) ─► Gemini (id 반복 + 긴 JSON, thinking=low) ─► 6문단 한꺼번에 렌더

적용 후
content.js ─(IntersectionObserver: 화면 + 아래·위 한 화면만)─► background ─► Edge Function
  ─► JWT 로컬 서명 검증 (네트워크 없음) ─► Gemini (번호 + [단어, 뜻] 쌍, thinking=minimal) ─► 렌더
```

클라이언트로 돌려주는 응답 형식 `{results:[{id, terms:[{surface, meaning}]}]}`은 **바뀌지 않았다.** 확장 프로그램 쪽 렌더링 코드도 그대로다.

## 1. 모델 출력 줄이기

파일: `supabase/functions/annotate/index.ts`, `supabase/functions/_shared/gemini.ts`

LLM은 입력은 병렬로 빠르게 읽지만 출력은 토큰을 **하나씩 차례로** 만든다. 그래서 응답 시간은 대략 `출력 토큰 수 ÷ 생성 속도`다. thinking 토큰도 답보다 먼저 하나씩 만들어지는 출력이라 같은 원리가 적용된다.

### 적용 전 / 후

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 모델에 보내는 문단 | `{"id":"pt-1730900000000-12","text":...}` | `{"i":0,"text":...}` |
| 모델이 쓰는 답 | `{"results":[{"id":"pt-…","terms":[{"surface":"x","meaning":"y"}]}]}` | `{"r":[{"i":0,"t":[["x","y"]]}]}` |
| 문단당 단어 수 | 2~8개 | 2~6개 (`MAX_TERMS_ASKED`) |
| thinking | `low` 고정 | `minimal` (`GEMINI_THINKING_LEVEL`), 모델이 거부하면 `low`로 자동 전환 |
| id 연결 | 모델이 id를 그대로 따라 씀 | 서버가 번호 → id로 연결. 모델은 id를 안 봄 |
| 사용량 로그 | 없음 | 호출마다 `gemini_call` 로그 한 줄 (ms, 입력·출력·thinking 토큰) |

### 예상 효과 (6문단 한 묶음, 단어 5개 기준)

| | 문단당 출력 | 묶음 출력 | 시간 (초당 150토큰 가정) |
|---|---|---|---|
| 적용 전 | 약 115토큰 | 약 690 | 약 4.6초 |
| 형식만 압축 | 약 70토큰 | 약 430 (−38%) | 약 2.9초 |
| 형식 압축 + 단어 상한 6개 | 실제 개수는 모델이 정하므로 그 이하 | | |
| thinking `minimal` | 위 값에서 thinking 분량만큼 더 줄어듦 | | 측정 필요 |

### 트레이드오프

- **번호로 연결하는 위험.** 순서만으로 맞추면 모델이 문단을 빼먹을 때 그 뒤 결과가 전부 한 칸씩 밀린다. 그래서 순서가 아니라 **번호(`i`)로** 연결하고 다음 순서로 처리한다.
  1. 번호로 찾는다.
  2. 없으면 예전처럼 id를 따라 쓴 경우를 찾는다.
  3. 둘 다 없고 **개수가 정확히 같을 때만** 순서대로 연결한다.

  모델이 번호를 잘못 쓰면 그 문단만 틀리고 다른 문단은 영향받지 않는다. id 방식과 비슷한 안전성이다.
- **단어 수 8 → 6.** C1/C2 사용자에게 "뽑아 줬으면 하는 단어"가 가끔 빠질 수 있다. 반대로 출력 상한이 줄어서 문단이 길수록 효과가 크다.
- **thinking `minimal`.** 문맥에 맞는 뜻 고르기(예: bank = 은행인지 강둑인지)와 숙어 인식이 조금 약해질 수 있다. **품질 위험이 가장 큰 항목이다.** 다만 `low`로 되돌리는 데 코드 수정이 필요 없다.
- **짧은 키(`r`, `i`, `t`).** 품질 영향은 거의 없다. 로그로 남긴 원문 응답을 사람이 읽기가 조금 불편해진 정도다.
- **자동 전환의 한계.** `minimal`을 지원하지 않는 모델이면 함수 인스턴스마다 첫 요청(들)이 400을 받고 `low`로 다시 호출한다. 그 요청들은 그만큼 느려지지만, 이후로는 그 인스턴스에서 계속 `low`를 쓴다.
  - 처음 구현에는 경쟁 버그가 있었다. 동시에 나간 요청 중 첫 요청만 `low`로 다시 호출하고, 나머지는 400 에러를 그대로 냈다. 지금은 각 요청이 자기가 보낸 thinking 수준을 기준으로 판단해서 고쳐졌다.
- **실제 확인 결과 (2026-11-06).** 현재 모델(`gemini-3.8-flash`)은 `"Thinking level MINIMAL is not supported for this model"`로 거부한다. 따라서 이 모델에서는 thinking 항목의 효과가 없다. 매번 생기는 400 왕복을 피하려면 시크릿 `GEMINI_THINKING_LEVEL=low`를 설정할 것.

### 조절 / 되돌리기

- thinking: Supabase 시크릿 `GEMINI_THINKING_LEVEL=low`로 설정한다. 재배포는 필요 없다.
- 단어 수: `annotate/index.ts`의 `MAX_TERMS_ASKED`를 바꾼다.
- 프롬프트를 바꾸면 `PROMPT_VERSION`을 올린다. 로그 label에 찍혀서 전후를 비교할 수 있다.

## 2. 서버 인증 왕복 없애기

파일: `supabase/functions/_shared/auth.ts`

### 적용 전 / 후

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 토큰 확인 | 요청마다 `supabase.auth.getUser()`로 Auth 서버에 왕복 | 프로젝트 공개키(JWKS)로 **함수 안에서 서명 검증**. 네트워크 없음 |
| 공개키 | — | 함수 인스턴스당 한 번 받아서 캐시. 최대 10분, 모르는 `kid`가 오면 다시 받음 |
| 검사 항목 | Auth 서버가 판단 | 서명, 만료, `aud=authenticated`, `role=authenticated`, `sub` 있음 |
| 예전 방식(HS256) 토큰 | — | 공개키로 검증할 수 없으므로 예전처럼 `getUser()` |
| 공개키를 못 받을 때 | — | `getUser()`로 대체 (서비스는 계속 동작) |
| 요청당 절약 | — | 왕복 한 번 (약 0.1~0.3초) + 요청마다 만들던 Supabase 클라이언트 |

### 트레이드오프

- **로그아웃·차단이 즉시 반영되지 않는다.** 로그아웃하거나 차단·삭제된 계정의 access token도 **만료될 때까지** 통과한다. 기본 만료는 1시간이다.
  - 일반 사용자는 영향이 없다. 로그아웃하면 확장 프로그램이 토큰을 지우고, refresh token도 무효가 된다.
  - 위험한 경우는 토큰이 **새어 나간** 경우뿐이다. 예: 개발자도구로 복사, 악성 확장 프로그램.
  - 사용량 제한(`consumeQuota`)을 다시 켜면 새어 나간 토큰으로 쓴 양도 그 사용자의 하루 사용량에 쌓인다.
- **anon/publishable 키 차단.** anon 키도 유효한 프로젝트 JWT다. 그래서 `role=authenticated`와 `sub`를 직접 검사한다. 테스트로 거부되는 것을 확인했다.
- **`verify_jwt`에 의존하지 않는다.** 서명을 함수 안에서 직접 검증하므로, 게이트웨이의 `verify_jwt`를 꺼도 위조 토큰은 통과하지 못한다.
- **issuer는 검사하지 않는다.** 로컬 개발(`supabase start`)에서는 `SUPABASE_URL`과 토큰의 issuer가 달라서다. 대신 이 프로젝트 JWKS로 서명이 맞는지 검증하므로, 다른 프로젝트가 발급한 토큰은 통과하지 못한다.
- **예전 방식 서명 키를 쓰는 프로젝트라면 효과가 없다.** 사용자 토큰이 HS256이면 매번 `getUser()`로 가서 속도 이득이 없다. 대시보드 → Settings → JWT Keys에서 비대칭 키(ES256/RS256)를 쓰는지 확인할 것.

### 위험을 줄이는 설정 (권장)

- Auth → **JWT expiry를 600~900초로** 줄인다. 위험 구간이 10~15분으로 줄어든다.
  - 확장 프로그램은 만료 1분 전에 자동으로 갱신한다(`refreshSessionIfNeeded`).
  - **주의:** 지금은 동시에 나간 요청들이 같은 refresh token으로 각자 갱신을 시도할 수 있다. 그러면 Supabase가 토큰 재사용으로 판단해 세션을 끊을 수 있다. 갱신 주기를 줄이면 이 일이 더 자주 생긴다. 그래서 만료를 줄이기 **전에** 갱신을 하나로 묶는 수정(단일 비행)을 먼저 하는 게 좋다. 이번 PR에는 포함하지 않았다.
- 사용량 제한(`consumeQuota`)을 다시 켠다.

## 3. 화면 근처 문단만 요청하기

파일: `extension/content.js`

### 적용 전 / 후

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 요청 대상 | 페이지의 모든 문단 (화면 안을 먼저) | **화면 + 위아래 한 화면**(`PREFETCH_MARGIN`) 안의 문단만 |
| 감지 방식 | `scroll` 이벤트와 DOM 변화마다 페이지 전체를 스캔하고 `getComputedStyle`, `getBoundingClientRect` 호출 | 새 문단 찾기만 디바운스(150ms)해서 스캔. 화면 근처 판단은 IntersectionObserver가 맡음. 스크롤 리스너 없음 |
| 확장이 넣은 DOM | 뜻풀이·형광펜을 넣을 때도 MutationObserver가 걸려 다시 스캔 | 확장이 넣은 노드(`.pt-gloss`, `.pt-highlight`, `.pt-banner`)만 바뀐 경우 무시 |
| 첫 요청 | 6문단 | **3문단**(`FIRST_BATCH`), 이후 6문단 |
| 스크롤 중 | 대기열에 남아 있으면 계속 요청 | 화면에서 멀어지면 대기열에서 뺌. 돌아오면 다시 넣음 |
| 하나씩 들어오는 문단 | 문단마다 즉시 요청 | 80ms(`INTERSECT_COALESCE_MS`) 모아서 한 요청 |

### 토큰 영향

요청마다 고정 프롬프트 약 200토큰이 반복된다. 묶음이 작아지면 요청 수가 늘어나 이 부분이 늘어난다.

**60문단 페이지를 끝까지 다 읽는 경우**

| 방식 | 요청 수 | 총 토큰 | 적용 전 대비 |
|---|---|---|---|
| 적용 전 (6개씩) | 10 | 약 14,600 | — |
| **적용 후 (첫 3개, 이후 6개)** | 11 | 약 14,800 | **+1.4%** |
| (참고) 모두 3개씩 | 20 | 약 16,600 | +14% |

**끝까지 안 읽는 경우.** 화면 근처만 요청하므로, 페이지 절반만 읽으면 요청하는 문단도 약 절반이다. 그래서 대부분의 실제 사용에서는 토큰이 **줄어든다.**

늘어나는 토큰은 전부 입력 토큰이고, 입력은 출력보다 단가가 싸다. 다만 thinking 토큰도 요청마다 붙으므로 요청 수가 늘면 같이 늘어난다.

### 트레이드오프

- **빠르게 스크롤하면 빈 문단이 잠깐 보인다.** 예전에는 페이지 전체를 미리 보내 두어서, 한참 기다린 뒤 아래로 내리면 이미 처리돼 있었다. 이제는 한 화면 앞까지만 미리 처리한다. `PREFETCH_MARGIN`을 `"200% 0px 200% 0px"`로 늘리면 줄어들지만 그만큼 안 읽는 문단에도 비용을 쓴다.
- **요청 수 증가.** 첫 3개 묶음과 스크롤 중 작은 묶음 때문에 요청 수가 조금 늘어난다. 그만큼 고정 프롬프트 토큰이 늘고, Gemini 분당 요청 한도(RPM)에 조금 더 빨리 닿는다. 80ms로 묶는 처리로 작은 요청이 쏟아지는 것은 막았다. 테스트에서 천천히 스크롤했을 때 문단 1개짜리 요청 대신 3, 3, 4, 6개로 묶였다.
- **새 문단을 늦게 발견한다.** 스캔 디바운스(150ms)와 묶기(80ms)만큼 늦다. 화면에 보이기 전에 한 화면 앞에서 처리되므로 체감은 거의 없다.
- **IntersectionObserver를 쓰는 쪽의 비용.** 코드가 조금 복잡해진다. 다시 스캔할 때(레벨 변경 등) 관찰을 끊고 새로 등록하는 처리가 필요하다(`resetIO`).
- **확장이 넣은 DOM 무시 규칙의 한계.** 바뀐 요소가 **전부** 우리 노드일 때만 무시한다. 텍스트 노드만 바뀐 경우는 다시 스캔한다. 예: SPA가 기존 `<p>`에 글자만 채워 넣는 경우.

### 조절

- `FIRST_BATCH`: 첫 요청 크기. 작을수록 첫 단어가 빨리 뜨지만 요청 수가 늘어난다.
- `PREFETCH_MARGIN`: 미리 처리하는 범위. 넓을수록 빠른 스크롤에 강하지만 비용이 늘어난다.
- `INTERSECT_COALESCE_MS`, `SCAN_DEBOUNCE_MS`: 묶는 시간. 길수록 요청 수가 줄지만 반응이 늦어진다.

## 측정 방법

배포 후 Supabase → Edge Functions → `annotate` → Logs에서 `gemini_call`을 검색한다.

```json
{"metric":"gemini_call","label":"annotate:compact-v1:n=6","model":"…","thinkingLevel":"minimal",
 "ms":2100,"promptTokens":740,"outputTokens":410,"thoughtsTokens":0}
```

- `ms`: Gemini 호출에 걸린 시간
- `outputTokens`, `thoughtsTokens`: 속도를 결정하는 값
- 비교하려면 같은 페이지로 적용 전(main 배포)과 적용 후를 각각 몇 번 로드한다. 그다음 `label`의 `n`(문단 수)이 같은 호출끼리 `ms`와 `outputTokens`를 비교한다.

## 검증한 것 / 안 한 것

- [x] Edge Function: `deno check` 통과. Gemini·JWKS·Auth를 가짜로 대신한 테스트 15개 통과.
  - 번호로 연결, 빠진 문단, 순서 뒤섞임, 예전 id 형식, 순서 대체
  - thinking 자동 전환
  - 정상 ES256 토큰, anon 거부, 다른 키로 서명한 토큰 거부, 만료 거부, HS256 → Auth 서버로 대체, Authorization 헤더 없음
- [x] content.js: 가짜 `chrome` API를 넣은 80문단 페이지에서 확인.
  - 첫 요청 3문단, 화면 근처만 요청
  - 확장이 넣은 DOM으로 다시 스캔하지 않음
  - 스크롤 중 묶기, 나중에 추가된 문단 처리, 레벨 변경 재스캔, 끄면 표시 제거
  - IntersectionObserver는 기하 계산으로 대신한 가짜를 썼다. 브라우저 창이 숨겨진 환경이라 실제 IO가 동작하지 않았다.
